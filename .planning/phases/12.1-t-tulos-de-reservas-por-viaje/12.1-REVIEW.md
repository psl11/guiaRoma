## Warnings

### WR-01: Non-Roma trips silently inherit Roma's headings, and only a README note guards against it

**File:** `app/utils/reservasHeadings.ts:46-52`, `shared/schemas.ts:368-372`, `tests/README.md:399-401`

**Issue:** The util's own docstring says Roma's headings are «información falsa» on any other trip (lines 5-7). Yet any trip whose `reservas.yml` omits `headings`, or omits a single key, gets those texts with no build or test failure:
- `z.strictObject` only catches misspelled keys. It does nothing about missing ones: every key is `.optional()`, and so is the object.
- The `unknown-key` rule only checks top-level keys.
- No invariant ties «trip ≠ roma» to «headings declared».

For example, if Campania (Phase 13) declares `mesas` and `visitas` but forgets `table`, it publishes «Restaurantes · cuándo reservar y con cuánta antelación» above a list of ferries and flights. The README note («Campania debe declarar `headings`…») is the only safeguard. This is the failure mode named in CAMP-04 / G-1.

**Fix:** Add a data invariant to `tests/data/invariants.spec.ts` / `tests/data/trips.ts`. It must not touch Roma's content (D-06) and must not change the schema. Schema `.optional()` stays as it is, per D-06 «all fields optional».
```ts
// reservas-headings: a non-Roma trip must title every block it renders
if (d.collection === 'reference' && d.data.slug === 'reservas' && t.dir !== 'roma') {
  const h = (d.data.headings ?? {}) as Record<string, unknown>
  const groups = new Set(((d.data.confirmed ?? []) as Array<{ group: string }>).map(c => c.group))
  const need = ['table', ...groups] // 'mesas' | 'visitas' only if that group has entries
  for (const k of need) if (!h[k]) push(d.file, 'reservas-headings', `falta headings.${k}: heredaría el texto de Roma`)
}
```
Add a teeth fixture for the new rule, then register `'reservas-headings'` in the rule list at `tests/data/trips.ts:93`.

### WR-02: A heading made only of spaces passes validation and renders as an empty `h4`

**File:** `shared/schemas.ts:369-371`, `app/utils/reservasHeadings.ts:50`

**Issue:** `z.string().min(1)` accepts `'   '`. I checked this: `z.string().min(1).safeParse('   ').success === true`. `resolveReservasHeadings` then keeps the value because `'   ' || default` is truthy. The template renders `<h4>   </h4>` and `<div class="reservas-box-header">     </div>`: a visible heading with no text above the confirmed list.

`min(1)` exists precisely to reject an empty heading, and a heading of spaces defeats it. The same thing happens with a YAML `mesas: " "`, or with a block scalar that contains only a newline.

**Fix:**
- In the schema, reject strings with no visible character: `z.string().regex(/\S/, 'encabezado vacío')`.
- In the resolver, fall back on blank values. Roma's defaults have no surrounding spaces, so its bytes do not change.
```ts
const pick = (key: ReservasHeadingKey): string => headings?.[key]?.trim() || RESERVAS_HEADINGS_DEFAULT[key]
```
- Extend `schema.spec.ts` with `parse({ headings: { mesas: '  ' } }).success === false`.
- Extend `reservasHeadings.spec.ts` with a `{ table: '  ' }` case that falls back to the default.

### WR-03: The D-03 empty-group rendering is not tested, and the wiring scan passes when the `v-if`s are misplaced

**File:** `tests/unit/reservasHeadings.spec.ts:91-95`, `tests/unit/reservasHeadings.spec.ts:139-147`

**Issue:** D-05 requires a test that an empty group is not rendered. Nothing here renders the component with an empty group:
- **Roma's fixture cannot cover it.** Both of Roma's groups have entries.
- **The `confirmed: []` test (lines 91-95) is tautological.** It only shows that filtering an empty array gives an empty array.
- **`wiringProblems` only counts substrings.** It checks that `v-if="mesas.length"` and `v-if="visitas.length"` each appear twice anywhere in the template. Each of these broken templates still passes:
  - `<h4 v-if="visitas.length">{{ headings.mesas }}</h4>` paired with `<h4 v-if="mesas.length" style="margin-top:.7rem;">{{ ` ${headings.visitas} ` }}</h4>`, so each heading is gated on the other group.
  - `<ul v-if="mesas.length"><li v-for="(c, i) in visitas">`.

  With either one, a trip with only `visitas` entries renders the wrong block. The README (§5.9) and the summary present this scan as the D-03 guard. The README also defers the browser check to Phase 13.

**Fix:** Bind each condition to its element and to the right list. The simplest way, with no new dependency, is element-scoped regexes:
```ts
const mustMatch: Array<[RegExp, string]> = [
  [/<h4 v-if="mesas\.length">\{\{ headings\.mesas \}\}<\/h4>/, 'h4 mesas'],
  [/<ul v-if="mesas\.length">\s*<li\s+v-for="\(c, i\) in mesas"/, 'ul mesas'],
  [/<h4\s+v-if="visitas\.length"\s+style="margin-top:\.7rem;"\s*>\s*\{\{ ` \$\{headings\.visitas\} ` \}\}\s*<\/h4>/, 'h4 visitas'],
  [/<ul v-if="visitas\.length">\s*<li\s+v-for="\(c, i\) in visitas"/, 'ul visitas'],
]
```
The better fix is a real SSR render. `vue` and `@vue/compiler-sfc` are already installed (transitively, via Nuxt):
1. Compile `ReservasSection.vue`.
2. Stub `MDC` and provide `resolveReservasHeadings`/`confirmedGroup` as globals.
3. Render it with `renderToString` for `{ confirmed: [visitas only] }` and for `{ confirmed: [] }`.
4. Assert there is one `h4` and no `.reservas-confirmadas`, respectively.

Replace the tautological test with one of these.

### IN-01: Heading keys and the group literal are defined twice, so they can drift from the schema

**File:** `app/utils/reservasHeadings.ts:36`, `app/utils/reservasHeadings.ts:57-59`, `shared/schemas.ts:368`

**Issue:** `ReservasHeadingKey` comes from `keyof typeof RESERVAS_HEADINGS_DEFAULT`, not from the zod `ReservasHeadings` shape, and that shape is not exported. If a fourth key is added to the schema without a default, the resolver drops it silently. TypeScript will not catch this: passing `props.reservas.headings`, which is not a fresh object literal, skips excess-property checks. `confirmedGroup` likewise hard-codes `'mesas' | 'visitas'` instead of using the schema enum.

**Fix:** Export `ReservasHeadings` and the group enum from `shared/schemas.ts`, then type the defaults against them:
```ts
export const RESERVAS_HEADINGS_DEFAULT = Object.freeze({ ... } satisfies Required<z.infer<typeof ReservasHeadings>>)
```
Derive the `group` parameter type from `ConfirmedGroup = z.infer<typeof ConfirmedGroupEnum>`.

### IN-03: The test relies on an invisible U+FE0F character, and the «sin U+FE0F» claim is not asserted

**File:** `tests/data/romaReservas.spec.ts:60-66`

**Issue:** Line 66 is `toContain('\u{1F39F}️')`. Its variation selector is a raw invisible byte sequence (`357 270 217`), not an escape. An editor or formatter that normalises the file would silently weaken the assertion. The title of the test at line 60 promises «sin U+FE0F tras ✅», but nothing checks that the character is absent. That claim rests only on the equality with the legacy `index.html`.

**Fix:** Use explicit escapes:
```ts
expect(RESERVAS_HEADINGS_DEFAULT.visitas).toContain('\u{1F39F}\u{FE0F}')
expect(RESERVAS_HEADINGS_DEFAULT.mesas).not.toContain('\u{FE0F}')
```

### IN-04: The byte gate can compare against a stale build when run on its own

**File:** `tests/data/romaReservas.spec.ts:74`

**Issue:** The post-build block runs whenever `.output/public/index.html` exists, whatever its age. Inside `pnpm verify` the build is fresh, because `verify` runs `rm -rf .data .nuxt .output` first. But a standalone `vitest run tests/data` after editing the template or the schema compares against an old build. It can pass or fail falsely. The project memory already records stale-build confusion (the Content cache).

**Fix:** Either document in the spec header that the result is only meaningful after a fresh `generate`, or skip with a warning when `.output/public/trips/roma/index.html` is older than `app/components/ReservasSection.vue`:
```ts
const stale = existsSync(BUILT) && statSync(BUILT).mtimeMs < statSync(join(ROOT, 'app/components/ReservasSection.vue')).mtimeMs
```
